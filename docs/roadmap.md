# 里程碑與執行順序

狀態：執行草案，2026-09-27。保留完整願景；所有 milestone 尚未驗收，沒有承諾日期。專案服務費以零元為限制，資料庫使用 Supabase，工具鏈採 Vite／Oxc 生態。依投入時間與試跑結果再估工，不以文件完成推定功能已完成。

## 里程碑

| 階段 | 成果與範圍 | 驗收標準 |
|---|---|---|
| M0 產品規則與可行性 | 五個核心流程、領域詞彙、跨日與取消規則；首發平台；通知／Widget／步數小驗證 | 影響第一輪實作的問題有答案或明確限制；每項驗證留下證據，不以查文件代替真機結果 |
| M0.5 開發迴圈試跑 | Vite 生態工具鏈、Supabase 本機環境／migration／RLS 驗證、任務卡、每週 30% 預算追蹤／停止、保存／接續機制；三張 pilot 任務 | 建立項目、兩時段同項目、手動補記能跑通；loop 中斷能接續、失敗能退出、完成能停止 |
| M1 項目與同步基礎 | 登入與資料隔離（Supabase Auth Free）、項目／標籤／基本筆記／下一步、跨裝置同步、自行匯出備份 | 兩端讀到同一份項目；網路失敗與編輯衝突可辨識；有基本備份可供恢復 |
| M2 可使用的週課表 | 七天配置、固定重複、當下首頁、單日異動、衝突選擇、草稿、生效日期、歷史版本 | 排一週；單日插入面試；改下週不動過去；跨午夜與時區案例符合已定規則 |
| M3 提醒、執行與補記 | 開始／結束提醒、狀態、手填時間、成果與下一步、補記、稍後／靜音／通知總覽 | 真機連續試用一週；漏記保持未知；改時或取消不留下有效的舊提醒；缺漏有清楚紀錄 |
| M4 待辦管理 | 項目／獨立待辦、多提醒、週期實例、跨項目列表／篩選、快速收件匣 | 搶票情境可用；本次完成不影響下次；收件匣可整理；重試不重複建立 |
| M5 筆記與知識整理 | 子頁面、內部／反向連結、附件、搜尋、模板、Markdown 匯入匯出、圖譜、封存、內容復原 | 長期項目能查找與接續；圖譜關係可切換；匯出再匯入保留支援範圍內的內容；封存符合已決規則 |
| M6 Dashboard 與回顧 | 時間分配、課表執行、項目進展、可選目標、每週回顧、調整下週入口 | 用已知資料核對報表；明示缺資料；取消／待補記分母規則一致；完成一次回顧與課表調整 |
| M7 專注與習慣 | 番茄鐘、專注模式、喝水提醒／飲水量、實際／目標作息、自訂數值與趨勢 | 記錄流程快速可用；計時器不自動覆蓋手填時間；可暫停提醒；無資料與零值分開 |
| M8 三端體驗與整合 | 手機／網頁／桌機完整操作、Widget、通知快速操作、唯讀行事曆、步數摘要 | 三端可接續；行事曆僅唯讀；授權拒絕可正常使用核心功能；Widget 與步數資料新鮮度可辨識 |
| M9 穩定使用與發布 | 備份還原演練、同步／通知可靠性、效能與錯誤處理、權限、免費可行的安裝與更新方式 | 三端至少兩週試用，無阻斷核心流程問題；實際還原成功；已知限制與發布方式記錄完整 |

## 依賴與可調整順序

- 建議主線：M0 → M0.5 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8 → M9。
- M0.5 需先驗證 Vite+ 相容性；網頁／共用套件採 Vite 生態，手機仍用 Metro。
- M0.5 只做切片驗證，不代表 M1 的同步、M2 的重複課表或 M3 的通知已完成。
- M6 的基本分析依賴 M2／M3／M4 的正確資料，不必等完整圖譜；若使用回饋顯示回顧更重要，可把 M6 的基本版提前。
- M7 的提醒能力沿用 M3；習慣趨勢沿用 M6。
- M8 是三端完整體驗；手機與第二個裝置的最小同步必須在 M1 就驗證。
- 手機原生能力在 M0 驗證可行性，在後續 milestone 完成產品化。
- 免費配額、備份、測試、存取控制與錯誤處理持續進行，M9 是整體驗收，不是第一次處理品質。

## 三個使用檢查點

| 檢查點 | 可以開始驗證的價值 | 使用者回饋重點 |
|---|---|---|
| M3 後：日常試用 | 排程、提醒、記錄能形成循環 | 是否每天願意記錄？提醒是否過多？ |
| M6 後：核心完整 | 項目、筆記、待辦、課表與回顧串接 | 是否能找到內容、接續工作與調整計畫？ |
| M9 後：完整願景 | 三端便利性與整合可長期使用 | 是否可靠？是否值得持續維護？ |

採 M3 日常試用、M6 核心完整、M9 完整願景作為版本檢查點；各版仍依實際驗收發布，不承諾日期。

## Milestone → Spec → Ticket／Issue → PR

每個 milestone 先展開成多份 spec，每份 spec 再展開成多張可獨立驗證／合併的 ticket。每票一個 issue 與自己的 PR，關聯原 spec 與 milestone。完整規則見[交付流程](delivery-workflow.md)，全體分組見[spec 索引](specs/README.md)。

產品票交付完整使用行為，含必要 UI、資料、API 與驗證；可以依賴已合併的基礎，不按前端／後端切出不可獨立驗收的票。例如 M2 的「當下安排與單日異動」spec，可再拆顯示當日安排、單日新增、單日改時、單日取消等獨立行為，各自列驗收與依賴。

近期 spec 先詳細化，後期先保留 Draft 分組；票在進入 Ready 前必須具備正文、真實 issue 與可執行驗收。第一批見[核心試跑 spec](specs/SPEC-M05-003.md)。所有子票完成後仍需 spec 整合驗收，再做 milestone 整體驗收。
