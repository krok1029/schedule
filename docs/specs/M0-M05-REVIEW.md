## 已經選項確認的規則

- 同一帳戶內項目名稱不可重複；忽略頭尾空白、大小寫、全形／半形差異，名稱中間空白仍有區別，畫面保留輸入樣式。
- 封存與 30 天復原期內都保留名稱；重新命名或永久刪除後才能重用。
- 項目名稱 1～80 字、下一步最多 2,000 字且可空白／清空、保留換行；超限顯示錯誤，不截斷。精確測試採 Unicode 字元（code point）計數，跨端一致。
- 重送同一請求與另一請求建立同名項目分開處理；前者安全重試，後者提示名稱衝突。
- 儲存失敗保留編輯內容、不顯示已儲存；原有時間、取消、封存、權限、同步與免費限制沿用。
- 驗收看外部行為、真實本機 Supabase 一般使用者權限與真機；純規則補單元測試。
- M0 驗證先隔離，不直接當正式功能；M0.5 三組核心能力仍要由 to-tickets 另拆票，舊編號不代表粒度已核准。

## 環境與執行邊界

Android 工具已安裝，模擬器尚未開機驗證，目前無真機連接也無手機骨架。相關票要有實際裝置才能做真機驗收。預算僅有監看式帳本，不宣稱平台硬性限額。既有文件／骨架尚未經 Git／PR 接軌。

## 確認後的動作

1. 以 to-spec 發布六份父 spec issues，分別歸到 M0／M0.5，附 ready-for-agent 標籤。父 spec 不當作實作 ticket。
2. 將本機草稿標記為來源指標，避免與遠端雙邊維護正文。
3. 以 to-tickets 提出每票成果與真正阻擋依賴，用選項確認粒度／依賴後才發布 ticket issues。
4. 每票個別 PR 關聯自己的 issue；不自動合併或發布應用程式。
