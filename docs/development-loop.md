# Loop engineering 執行草案

狀態：方向與預算已確認，執行機制待試跑。更新：2026-09-27。本文描述未來工作方式，沒有建立排程、自動化或背景執行程序。

## 原則

使用者決定產品行為與優先順序；agent 在已定義範圍內實作、驗證與修正。每輪選擇明確任務，有可重現證據、持久進度與停止條件。

參考 [Addy Osmani：Loop Engineering](https://addyosmani.com/blog/loop-engineering/) 的選工作、分派、檢查、保存與接續觀念；本專案的任務狀態、試跑額度及驗收流程是自行設計的提案。

## 一輪如何執行

1. **恢復上下文**：讀產品規則、任務卡、目前版本與上輪紀錄；核對工作目錄與實際修改。
2. **選擇任務**：沿 milestone → spec 找一張有真實 issue 的 Ready ticket，確認依賴都已合併並驗證。沒有 Ready 任務就退出，不自行擴大需求。
3. **建立隔離環境**：使用任務分支；有並行或隔離需求才加 worktree。初期只允許一個實作任務進行。
4. **實作與驗證**：依驗收案例完成最小行為，跑適用的規則測試、整合測試或實際操作。
5. **獨立檢查**：審查原始需求、當前 diff 與實際結果；找出缺漏與回歸，不只閱讀實作者摘要。
6. **修正或結束**：有具體失敗原因且未達額度就修正；需求阻礙、沒有進展或到上限就保存並退出。
7. **個別 PR 與交付**：每票開自己的 PR，關聯對應 issue、spec 與 milestone，附驗收證據。審查完成後待使用者合併；整合後驗證通過才 Done。spec 與 milestone 另做整體驗收。

獨立審查可採新的 agent 上下文或人工審查；使用 subagent 時只負責界定的審查工作。起步不建立多個實作者同時修改資料模型的工作方式。

## 任務生命週期

| 狀態 | 定義 | 下一步 |
|---|---|---|
| Draft | 還有未定規則、依賴或驗收缺口 | 補規格 |
| Ready | 範圍、依賴、驗收、環境與執行額度已具備 | 可被選取 |
| In Progress | 已指定執行者與工作版本 | 實作／驗證 |
| In Review | 本票 PR 已開且關聯 issue，提交與驗收證據已備妥 | 獨立檢查 |
| Verified | 當前版本通過該卡驗收 | 等待按約定方式整合 |
| Done | 已整合到目標版本，整合後檢查通過 | 依賴可繼續 |
| Blocked | 缺少產品決定、外部條件，或已證實無法繼續 | 列明需要的輸入 |
| Budget Exhausted | 達到執行上限 | 保存工作，調整額度或重新拆卡 |

這是專案任務卡的狀態定義，不等同任何 agent 產品內建的目標狀態。Verified 不等於已合併或已發布。

## Ready 與完成條件

交付層級與真實來源以[交付流程](delivery-workflow.md)為準。Ready 卡至少包含：milestone、spec 路徑／版本／AC 編號、真實 issue URL、使用情境、允許修改範圍、不在範圍、依賴、具體驗收、驗證方式、待決問題清空、批次額度。範例與模板見 [pilot](tasks/pilot.md)、[TEMPLATE](tasks/TEMPLATE.md)。

完成還需符合[程式碼規範](coding-standards.md)：SOLID、受管程式檔最多 600 行，僅測試與純樣式檔例外；審查拆分責任與依賴方向。本機行數檢查已納入 `pnpm check`，拆分品質仍須審查。

完成證據必須對應當前版本。測試通過後若程式又修改，應重跑受影響的驗證；審查發現與規格衝突時不能直接降低測試要求。

## 工具與費用限制

- Vite／Oxc 生態為已定方向，Vitest 作為網頁與共用規則的主測試工具；實際命令依 Vite+ 選定版本填入任務卡。
- Supabase 本機 migration、RLS／RPC、兩個使用者的資料隔離要有整合驗證；Free 雲端只做必要的部署驗證。
- 不使用付費 CI、遠端快取或額外購買的 agent API 用量。套件本機工具不收服務費，帳戶配額仍需設定上限。
- 缺少免費額度時保存進度並停止，不自動升級方案或啟用付費服務。

## 驗證策略

| 層次 | 適用行為 | 證據 |
|---|---|---|
| 規則驗證 | 單日異動、課表版本、待補記、週期待辦、報表分母 | 可重現案例與斷言 |
| 整合驗證 | 儲存、唯一性、同步衝突、權限、重試 | 本機 Supabase／真實 PostgreSQL 下的結果 |
| 使用流程 | 建項目、由兩個時段接續、補記、每週回顧 | 操作結果與必要截圖 |
| 平台驗證 | 背景通知、Widget、健康授權、裝置同步 | 真機型號／系統版本／測試條件與限制 |

重點是產品行為，不為了數量寫重複實作的測試。時序測試應可控制時間；真機證據不以模擬輸出代替。第一輪尚未選定工具時，不在文件假裝已有可跑命令。

## 預算與停止規則

- 試跑建議每批最多 1 張卡，同一失敗最多 3 次有明確假設的修正；無新增證據就停止重複嘗試。
- 每批必須設定實際時間上限及可執行的成本／用量限制。每批上限 60 分鐘，全專案每週合計最多使用帳戶週總上限的 30%，在 28 個百分點停止開新輪次。定義與限制見[agent 預算](agent-budget.md)；不能把比例直接換成 token。
- 預算政策與監看式帳本已建立，尚無自動讀值執行器或平台硬性限制。M0.5 要驗證讀值、記帳、預警與停止的完整操作；若無法強制限制單輪，就保持有人監看、一次一任務的模式。
- 達到上限不算成功，不為了關閉任務而填 Done。
- 停止時保留檔案、目前版本、失敗證據、已嘗試方法與可接續步驟。
- 使用者停止指示、需要變更已確認產品行為、無法取得必要憑證或環境時，也應退出並報告。

## 進度持久化與觸發

規格正文保存在儲存庫；ticket 建立遠端 issue 後，以 issue 管理狀態、證據與 PR 連結。本機 ticket 草稿只留來源索引，不雙邊維護狀態。遠端 repo 尚未指定時先保存草稿，不能宣稱 issue／PR 已建立。自動觸發仍待試跑成功後評估。

每輪保存任務 ID、規格版本、base／目前提交、工作分支、變更範圍、驗證結果與路徑、嘗試次數、剩餘額度、阻礙與下一步。詳細日誌和截圖可放獨立執行產物區，任務卡留索引；不可存入密鑰或私人健康資料。

未來執行器應檢查「同一任務是否已有執行者」，並用執行識別與鎖定避免重複啟動。從失敗恢復時先核對已完成副作用，再決定重試。初期使用者手動啟動一批，系統在批次內循環；排程與事件觸發留到試跑成功後。

## 自主範圍

Ready 卡內的一般程式變更、檢查與修正可自行進行；執行前已約定的可逆操作不需逐步詢問。原 open questions 已授權依建議執行，預設見[決策紀錄](open-questions.md)；範圍內可逆細節自行處理並記錄，新增功能與重大語意變更再提出。

預設允許在任務分支做本機 checkpoint commit。使用者已明確指定每票 issue／PR 交付：確認 repo 後，可為已定案 ticket 建 issue、push 任務分支並開對應 PR，不逐票重問；合併與發布仍由使用者決定。原建議的確認不等於排程或無人值守長任務已啟動，也不授權付費服務。

## 試跑評估

前三張卡記錄：人工介入次數、修正輪數、驗收漏掉的問題、重啟是否成功、時間與用量。依證據調整任務粒度、上下文與驗證方式，再考慮擴大每批任務數。
