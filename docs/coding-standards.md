# 程式碼風格與可讀性

狀態：已確認規範，2026-09-27。使用者要求維持 SOLID，除測試與樣式檔外，超過 600 行必須拆檔；工具優先採較新或主流方案。

## SOLID 的落地方式

| 原則 | 本專案的做法 |
|---|---|
| S：單一職責 | 畫面呈現、表單驗證、查詢狀態、資料存取、領域計算分開；例如一個課表元件不同時處理 Supabase 查詢與跨日統計 |
| O：開放封閉 | 新增提醒方式或外部來源時，以實際需要的組合／策略擴充，避免把每種平台分支塞進核心流程 |
| L：里氏替換 | 同一 Interface 的 Adapter 維持一致的輸入、結果與錯誤語意；測試替身不能比真實資料庫更寬鬆而掩蓋行為 |
| I：介面隔離 | 呼叫者只需要與當前工作相關的能力，不用接收包含所有功能的巨型物件 |
| D：依賴反轉 | 時間、資料讀寫與平台通知從外部注入；核心計算不直接依賴 React、Supabase SDK 或手機 API |

Module 透過小而清楚的 Interface 隱藏複雜 Implementation；需要替換行為的位置是 Seam，具體外部整合是 Adapter。介面包含失敗模式與使用條件，不只是 TypeScript interface 宣告。

可用函式、hooks、組合與依賴注入實踐，不要求全部改成 class。只為有實際變化或測試需求的依賴建立 Seam；避免每個 CRUD 都多一層只有轉呼叫的空殼。

## 600 行硬性規則

- 以**單一檔案的實體行數**計算，包含空白與註解；600 行可接受，601 行必須拆分。
- 適用於本專案程式碼，包含 TS／TSX／JS、SQL、Rust、Kotlin、Swift、腳本與程式型設定；未來新增語言也適用。
- 唯二程式碼例外：測試檔與純樣式檔。測試可以按案例拆分，但不套 600 行上限；樣式檔仍須可讀。
- `*.test.*`、`*.spec.*`、`*.e2e-spec.*` 與確實只供測試使用的檔案屬測試範圍；目錄或檔名不能掩護產品邏輯。
- CSS／SCSS／Less 與只有樣式宣告的 style module 屬樣式範圍。含 Tailwind class 的 TSX、Tailwind 程式型設定、含行為的 CSS-in-JS 仍是一般程式碼。
- 文件、套件鎖定檔、第三方依賴、編譯產物不是本規則的原始碼檢查對象；不能藉此將自己維護的程式碼排除。
- 自動產生且納入本專案的程式碼**不因 generated 標記而自動豁免**；須選可分檔生成方式，若工具做不到則提出具體限制，不擅自新增例外。
- 不刪合理註解、不塞多個敘述在一行、不把產品程式藏進測試／樣式檔來達標。

拆檔以責任與變更理由為準。例如將課表功能分為日期運算、資料存取、query hooks、表單 schema 與畫面；同一功能的內部檔案放在一起，保留少量對外 Interface，避免大量零碎轉接與循環 import。

SQL 同樣需控制長度。新的 migration 可按相依順序分檔；已套用的 migration 不為縮行改寫歷史，以後續 migration 修正。

## TypeScript 與資料流

- 啟用 strict；避免用 `any`、非必要斷言或重複手寫型別掩蓋問題。外部未知值以 `unknown` 接入，再透過 schema 確認。
- Zod 用在表單、匯入、外部回應與函式入口等信任轉換處；已驗證的內部資料不需每層重複 parse。
- Supabase 產生的資料庫型別與 Zod 的 runtime schema 職責不同；不要把資料庫原始欄位直接當所有畫面模型。
- TanStack Query 管伺服器資料與快取；表單輸入、彈窗、選取狀態等留在適當的本機狀態，不建立第二套相同伺服器快取。
- query key 包含資料範圍與必要身分；登出／切帳戶清理對應快取。查詢呼叫資料存取 Module，畫面不直接散佈 Supabase 查詢。
- 明確處理載入、空資料、失敗、過期、衝突與未儲存狀態；免費流量與通知正確性需納入重試／刷新設計。

## 工具選型原則

預設網頁組合為 React、Tailwind CSS、Zod、TanStack Query，與 Vite+ 工具鏈搭配；依[工具鏈文件](toolchain.md)確認用途與平台差異。

優先採官方仍維護、文件完整、主流生態且相容的穩定版本。新工具需解決具體問題；新增依賴要能說明用途、免費／授權條件、跨平台支援與替代成本。版本寫入 manifest／鎖定檔；預發行套件若為相容性所需，先記錄理由與風險。

## Loop 與驗收

M0.5 建骨架時加入可重現行數檢查，枚舉受控原始碼與測試／純樣式例外；601 行應失敗，600 行應通過。若 lint 工具無法涵蓋所有語言，以簡單額外檢查補足，不能默默漏查 SQL 或原生碼。

每張卡除功能驗收外，也檢查檔案行數、SOLID、命名、呼叫方向及是否濫用抽象。新增或修改的程式需通過適用格式、lint、型別與測試；改 API／RLS 要加對應整合證據。

本機行數檢查已實作：`pnpm check:lines`，並納入 `pnpm check`；601 行會失敗。涵蓋目前 TS/JS 與已規劃 SQL、Rust、Kotlin、Swift 等程式副檔名；新增語言時須擴充 `scripts/source-files.mjs`。測試以 `.test.*`／`.spec.*`／`.e2e-spec.*` 辨識，純 CSS／SCSS 不計入；不得藉改名規避。**CI 尚未設定**。
